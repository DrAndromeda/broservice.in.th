## 0. Non-negotiable working rules

- Start by inspecting the repository, current branch, latest commit, file tree, git status and existing uncommitted changes. Preserve user work.
- Create a dated backup or rollback branch before substantial edits. Never reset, force-push, rewrite history or replace the repository with another copy.
- The existing repository and live site are the baseline. Compare them before changing architecture or copying files.
- Work in small, reviewable phases. Keep a changelog and record commit SHAs.
- Do not deploy, alter DNS/Cloudflare, change production redirects or replace live files without explicit owner approval.
- Never invent services, prices, discounts, service areas, opening hours, warranties, response times, staff, qualifications, licenses, reviews, ratings, addresses or guarantees.
- Never commit passwords, API keys, Telegram tokens, customer information or private operational files.
- Keep all customer-facing content consistent with the actual services and operational capacity.
- If a requirement cannot be verified, mark it BLOCKED / OWNER CONFIRMATION REQUIRED; do not silently guess.
- Do not create mass-produced doorway pages or keyword-swapped thin pages.

## 1. Project goal and quality benchmark

Develop BroService into a polished, trustworthy, conversion-focused local service website for the actual services and coverage confirmed by the owner. The site should feel like a professionally designed commercial brand, not a generic template or an SEO text dump.

Use the quality lessons established during the FORMA and CreativeLAB projects:
- Clear information architecture and consistent page templates.
- Strong, readable typography, generous spacing, restrained visual hierarchy and consistent brand styling.
- Distinctive, relevant imagery rather than unrelated stock photos.
- Excellent mobile behavior and predictable navigation.
- Complete, useful service pages with real explanations, process, scope, limitations, FAQs and clear contact actions.
- Multilingual content that reads naturally in each language.
- Search-engine and answer-engine discoverability built on accurate, crawlable HTML.
- No fake trust signals, keyword stuffing or unsupported claims.

Do not copy FORMA's luxury visual identity or CreativeLAB's agency style. Reuse their engineering, editorial, SEO and QA standards while preserving BroService's own brand identity.

## 5. Phase 4 — Content architecture and editorial standard (P0)

### Homepage

- [ ] Write a concise, specific H1 describing the real primary service and relevant location without awkward keyword repetition.
- [ ] Explain the service proposition, target customers, actual coverage and next step immediately.
- [ ] Add clear links to the principal service pages.
- [ ] Explain the process and what a customer should expect, using only verified operational facts.
- [ ] Include genuine trust information only where evidence exists.
- [ ] Add a concise FAQ section based on real customer questions. The visible questions and answers must exactly correspond to any FAQ structured data.
- [ ] Make contact/order actions prominent and consistent.

### Service pages

- [ ] Create a dedicated page for each genuinely distinct core service, based on the services already offered and confirmed by the owner.
- [ ] Each important service page should normally contain approximately 1,000–1,500+ words only when that length is justified by useful subject matter. Do not pad pages to hit a word count.
- [ ] Use a clear H1 and logical H2/H3 hierarchy.
- [ ] Explain: what the service includes, who needs it, common use cases, the process, preparation, scope, exclusions, factors affecting price, expected deliverables and how to request it.
- [ ] Add comparison or pricing tables only when current prices and terms have been confirmed. Clearly state units, inclusions, exclusions and date/conditions.
- [ ] Add original FAQs that answer practical questions; avoid repeating the same generic FAQ on every page.
- [ ] Link contextually to related services, contact information and relevant coverage pages.
- [ ] Add relevant real images, captions and descriptive alt text.
- [ ] Avoid repeating identical blocks across pages with only the city/service keyword changed.

### Location and supporting pages

- [ ] Create a location page only where the business genuinely serves that area and can provide useful, distinct local information.
- [ ] Do not imply a staffed branch or physical office at a service-area location unless it exists and is confirmed.
- [ ] Provide a useful About, Contact and privacy/legal information page appropriate to the actual business.
- [ ] Ensure contact details, opening hours, service coverage and policies match across the site.

### Multilingual editorial process

- [ ] Treat English as the source language unless the owner specifies otherwise.
- [ ] Translate and localize all substantive page content into RU, TH and HE; do not publish machine-literal or incomplete translations.
- [ ] Use native-sounding terminology, correct spelling, localized calls to action and culturally appropriate formatting.
- [ ] Keep prices, units, service terms, contact details and factual claims identical across translations.
- [ ] Do not publish a language variant as complete if it contains untranslated placeholders, mixed-language navigation or missing critical content.
- [ ] Have uncertain Thai/Hebrew technical terms flagged for owner/native-speaker review.

## 6. Phase 5 — SEO, local SEO, GEO and structured data (P0/P1)

- [ ] Give every indexable page a unique, descriptive title, meta description, one clear H1, correct lang attribute and self-referencing absolute canonical.
- [ ] Use clean, stable, human-readable URLs. Define one trailing-slash policy and enforce it consistently.
- [ ] Implement reciprocal hreflang for EN, RU, TH and HE equivalents, plus x-default only when appropriate. Never reference missing translations.
- [ ] Add accurate Open Graph and social metadata; verify every image URL resolves.
- [ ] Add descriptive image alt text; do not stuff keywords into alt attributes.
- [ ] Create and validate XML sitemap(s). Include only canonical, indexable, intended 200-status pages; exclude 404 pages, redirects, noindex pages and duplicates.
- [ ] Ensure robots.txt references the correct live sitemap and does not block important HTML, CSS, JS or image resources.
- [ ] Maintain an accurate /llms.txt describing real services, locations, languages and contact routes. Do not add claims that are absent from visible pages.
- [ ] Review AI crawler access policy. Distinguish search/answer retrieval bots from model-training crawlers; implement only the owner's approved policy and verify the effective live robots response, including Cloudflare-managed behavior.
- [ ] Use Schema.org JSON-LD only when it accurately represents visible page content. Consider LocalBusiness/appropriate subtype, Organization, Service, BreadcrumbList and FAQPage where eligible and justified.
- [ ] Use one stable business entity @id across the site. Keep name, URL, phone, email, address, service area and opening hours consistent with verified public information.
- [ ] Never invent a street address, map pin, rating, review, price, aggregateRating, credential or service guarantee.
- [ ] FAQPage markup must match visible FAQs exactly. Do not add hidden FAQ content for SEO.
- [ ] Validate representative pages with Schema.org Validator and Google Rich Results Test; fix meaningful errors.
- [ ] Add contextual internal links and breadcrumbs. Avoid orphan pages and long redirect chains.
- [ ] Do not promise rankings, indexing, rich results or AI citations.

## 7. Phase 6 — Performance, accessibility and security (P1)

- [ ] Serve important content as crawlable HTML, not solely through client-side rendering or images.
- [ ] Optimize hero/LCP imagery; use modern formats and responsive sizes while retaining original assets.
- [ ] Do not lazy-load the actual LCP/hero image. Lazy-load below-the-fold images.
- [ ] Set image width and height or aspect ratio to prevent layout shift.
- [ ] Minimize unnecessary JavaScript, CSS, fonts and third-party scripts. Use caching and compression appropriate to the host.
- [ ] Measure Core Web Vitals on representative live pages: target LCP < 2.5s, INP < 200ms and CLS < 0.1; report measured results, not estimates.
- [ ] Ensure keyboard navigation, visible focus, sufficient contrast, semantic headings, form labels and meaningful link text.
- [ ] Add appropriate security headers only after checking compatibility with required assets and integrations.
- [ ] Check for exposed secrets, private files, debug output, directory listings, unsafe embeds and mixed content.
- [ ] Ensure forms validate input and fail gracefully. Do not send real customer messages during testing without authorization.

## 8. Phase 7 — Conversion and analytics readiness (P1)

- [ ] Make the main conversion action obvious and consistent on desktop and mobile.
- [ ] Use working tel:, WhatsApp, Telegram, email or form links only where the destination is verified.
- [ ] Explain what information a customer should provide when requesting a quote or service.
- [ ] Ensure form errors and success states are clear and accessible.
- [ ] Test contact flows with an explicitly authorized test destination; do not contact real customers.
- [ ] Add analytics or advertising pixels only after the owner provides the correct IDs and approves privacy/consent behavior.
- [ ] Do not fabricate conversion statistics or testimonials.

## 9. Phase 8 — Technical implementation and production readiness (P0)

- [ ] Preserve the current static-site approach unless the owner explicitly approves an architectural change.
- [ ] Ensure all internal links and asset paths work from the actual production document root, not just localhost or a repository preview.
- [ ] Check case-sensitive paths, encoded URLs, MIME types, font/image paths and relative links.
- [ ] Ensure custom 404 pages return a real HTTP 404 status.
- [ ] Confirm redirects are one-hop, intentional and do not create loops.
- [ ] Verify HTTPS, host normalization and trailing-slash behavior.
- [ ] Keep staging and production configuration separate. Never publish staging URLs, localhost references or development paths in canonical tags, sitemap, Open Graph or JSON-LD.
- [ ] Prepare a deployment manifest listing exact files to upload, destination paths, backup steps and rollback steps.
- [ ] Do not upload secrets, source backups or internal TODO files into the public document root.
- [ ] Production deployment requires owner approval. After deployment, test the actual public URLs.
